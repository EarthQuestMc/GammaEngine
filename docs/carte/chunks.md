# Carte du code — chunks

Conventions. `E:` = `eclipse/cauldron/src/main/java/` (sources patchées, hors git). `S:` = `src/main/java/`. Les numéros de ligne sont ceux du workspace local. Threads : MAIN = thread de tick ; CIO = « Chunk I/O Executor Thread-N » (daemon, Forge) ; FIO = « File IO Thread » (priorité 1, vanilla) ; NET = boucle d'événements Netty ; LIGHT = « PaperSpigot - Lighting Thread » (inactif en pratique, voir pièges). Éléments propres à GammaEngine côté chunks : `S:io/github/gammaengine/world/ChunkPrefetcher.java` (deux appels dans `MinecraftServer.initialWorldChunkLoad`, lignes 472 et 492), `ScratchBuffers` et niveau de deflate configurable dans `S21PacketChunkData` et `S26PacketMapChunkBulk` ; tout le reste vient de Forge, Cauldron, Thermos, Spigot, Paper ou Crucible. `eclipse/Clean` est Forge + Minecraft sans aucun de ces apports (pas de CraftBukkit), donc `patches/` y mélange Cauldron, Spigot et Crucible.

## Vue d'ensemble

Résumé des threads, étape par étape (détail et preuves dans les sous-sections) :

| Flux | Étape | Thread |
| --- | --- | --- |
| Chargement (chunk sur disque) | test d'existence, mise en file, étape 2 (entités, TileEntities, événements, `populateChunk`) | MAIN |
| | lecture région, inflate, NBT, construction du `Chunk` et des sections | CIO (ou MAIN si `syncChunkLoad`) |
| Génération | terrain, structures, `populate`, `BlockPopulator`, `IWorldGenerator` des mods | MAIN |
| Déchargement | file, `ChunkUnloadEvent`, `onChunkUnload`, sérialisation NBT | MAIN (100 chunks par tick au plus) |
| Sauvegarde | autosave complète, `level.dat`, joueurs, `WorldSavedData` | MAIN |
| | deflate et écriture des régions | FIO (un seul thread) |
| Envoi | file par joueur, extraction des sections, `S26PacketMapChunkBulk` | MAIN |
| | deflate (`compress`) et écriture réseau | NET |
| Lumière | propagation, `generateSkylightMap`, recheck des trous | MAIN (variante LIGHT inopérante) |

### Chargement (existe sur disque)
1. MAIN : `ChunkProviderServer.loadChunk(x,z,Runnable)` (`E:net/minecraft/world/gen/ChunkProviderServer.java:174-213`) vide `chunksToUnload` pour ce chunk (176), puis teste `AnvilChunkLoader.chunkExists` (189). Ce test ouvre éventuellement un `RegionFile` (`RegionFileCache.createOrLoadRegionFile(...,false)`, verrou statique `RegionFileCache.java:25`) et prend le moniteur du `RegionFile` (`RegionFile.java:109`) : MAIN peut attendre un thread qui lit ou écrit la même région.
2. Avec callback (c'est le cas de `PlayerManager.PlayerInstance`, `PlayerManager.java:408,441`) : `ChunkIOExecutor.queueChunkLoad` (`ChunkProviderServer.java:193`), retour `null`. Sans callback : `syncChunkLoad` (198) = étapes 1 et 2 sur le thread appelant, ou attente de la tâche si elle est déjà lancée (`AsynchronousExecutor.java:338-346`, `Task.initSync` 122-146).
3. CIO, étape 1 (`ChunkIOProvider.callStage1`, `E:net/minecraftforge/common/chunkio/ChunkIOProvider.java:18-33`) : `AnvilChunkLoader.loadChunk__Async` (`AnvilChunkLoader.java:102-138`) lit les octets sous le moniteur du `RegionFile` (`RegionFile.java:113-165`), inflate et décode le NBT (`CompressedStreamTools.read`, 134), puis `readChunkFromNBT` (428-475) : `new Chunk`, `ExtendedBlockStorage`, `NibbleArray`, `removeInvalidBlocks`. Aucun événement n'est émis ici.
4. MAIN, étape 2 (`callStage2`, `ChunkIOProvider.java:36-77`), déclenchée par `ChunkIOExecutor.tick()` (`MinecraftServer.java:930-932`, avant le tick des mondes) : `loadEntities` (43) crée entités, TileEntities et TileTicks sur MAIN (`AnvilChunkLoader.java:477-575` : `EntityList.createEntityFromNBT` 488, `TileEntity.createAndLoadEntity` 526, ticks 568), `ChunkDataEvent.Load` (44), insertion dans `loadedChunkHashMap_KC` et `loadedChunks` (46-47), `onChunkLoad` + `ChunkEvent.Load` (48) (`Chunk.java:1033-1051`), `recreateStructures` (52), `ChunkLoadEvent` Bukkit (58), compteurs de voisins 5×5, puis `populateChunk` (76). Si l'étape 1 renvoie `null` (fichier illisible ou lecture échouée), `originalLoadChunk` est appelé sur MAIN (39) : il retente `safeLoadChunk` (`ChunkProviderServer.java:232`) et ne génère que si cette seconde lecture échoue aussi.
5. Pool CIO : 1 thread + 1 par tranche de 50 joueurs (`ChunkIOExecutor.java:6-7,24-27`), réajusté à la connexion et à la déconnexion (`ServerConfigurationManager.java:383,461`). File `LinkedBlockingQueue` non bornée, FIFO (`AsynchronousExecutor.java:234`). `tasks` est un `HashMap` non synchronisé, réservé à MAIN (220).

### Chargement synchrone et génération
- Chemin sans fichier : `originalLoadChunk` (`ChunkProviderServer.java:215-302`), tout sur MAIN : `ForgeChunkManager.fetchDormantChunk` (229), sinon `safeLoadChunk` (232, lit le disque en direct), sinon `currentChunkProvider.provideChunk` (245) = génération du terrain. Puis insertion (261-262), `onChunkLoad`, `ChunkLoadEvent(newChunk)` (279), voisins (283-295), `populateChunk` (297). Garde de ré-entrance par `loadingChunks` (224-228, simple avertissement).
- `Chunk.populateChunk` (`Chunk.java:1182-1205`) appelle `ChunkProviderServer.populate` quand les trois voisins +x/+z/+xz sont chargés, pour le chunk et ses trois voisins arrière.
- `ChunkProviderServer.populate` (418-464), MAIN : `currentChunkProvider.populate` (429, génération vanilla ou mod, événements `PopulateChunkEvent.Pre/Post` dans `ChunkProviderGenerate.java:382,453`), `BlockPopulator` Bukkit avec `worldObj.populating` (439-454), `ChunkPopulateEvent` (457), `GameRegistry.generateWorld` (459) = tous les `IWorldGenerator` des mods.
- Déclencheurs synchrones (tous sur MAIN) :
  - (a) `provideChunk` → `loadChunk` si `shouldLoadChunk()` (309, 617-623) : vrai si `loadChunkOnProvideRequest` (défaut vrai), pendant la recherche du spawn, pendant l'événement Forge de tick avec `loadChunkOnForgeTick`, ou dans les 100 premiers ticks du fournisseur ; sinon renvoie `defaultEmptyChunk` (chunk vide en 0,0). C'est le chemin de tout `getBlock` d'un mod sur une zone non chargée.
  - (b) chunks forcés par ticket : `World.setActivePlayerChunksAndCheckLight` appelle `loadChunk(x,z)` à chaque tick pour tout chunk forcé non chargé (`World.java:3473-3481`).
  - (c) API Bukkit `CraftWorld.getChunkAt` et `loadChunk(x,z,true)` (`S:org/bukkit/craftbukkit/v1_7_R4/CraftWorld.java:150,277-282`) ; `loadChunk(x,z,false)` lit via `safeLoadChunk` sans passer par le pool (même fichier, 290).
  - (d) tickets d'entité restaurés au chargement du monde (`ForgeChunkManager.java:486-492`).
  - (e) démarrage : `MinecraftServer.initialWorldChunkLoad` (`MinecraftServer.java:455-495`, 25×25 = 625 chunks du monde 0, rayon 192 codé en dur) ; autres mondes via `CraftServer.createWorld` si `keepSpawnInMemory` (`S:org/bukkit/craftbukkit/v1_7_R4/CraftServer.java:936-957`, rayon 196, boucle séquentielle non préchargée).
  - (f) `PlayerInstance` pour un chunk absent du disque : génération dans `addPlayer` ou `updatePlayerPertinentChunks` (`PlayerManager.java:408`), donc au milieu du tick du joueur.
- Journalisation existante : `cauldron.logging.chunkLoad` → `CauldronHooks.logChunkLoad` (`S:net/minecraftforge/cauldron/CauldronHooks.java:89-97`), appelée à chaque `loadChunk` (`ChunkProviderServer.java:186`, y compris pour un chunk déjà chargé) et à `safeLoadChunk` (354), avec pile complète, sans compteur, sans distinction synchrone ou asynchrone. Timings Spigot `syncChunkLoad*` (`ChunkProviderServer.java:223,298,363`, `S:co/aikar/timings/WorldTimingsHandler.java:47`) et `MinecraftTimings.chunkIOTickTimer` (`MinecraftServer.java:930-932`).
- Structures : `recreateStructures` est appelé à chaque chargement depuis le disque (`ChunkProviderServer.java:364`, `ChunkIOProvider.java:52`) ; pour un monde normal avec `generate-structures=true` il lance quatre `MapGenStructure.func_151539_a` (mineshaft, village, stronghold, temples) de rayon 8, soit 4 × 289 candidats par chunk (`ChunkProviderGenerate.java:495-505`, `E:net/minecraft/world/gen/MapGenBase.java:15-30`), sur MAIN.

### Déchargement
- Mise en file : `unloadChunksIfNotNearSpawn` (`ChunkProviderServer.java:108-155`), appelée à la sortie du dernier joueur d'un `PlayerInstance` (`PlayerManager.java:495`), par `WorldServer.saveAllChunks` pour tout chunk non observé (`WorldServer.java:1093-1104`), par `unloadAllChunks` quand un monde sans respawn est vide (`PlayerManager.java:92-105`) et par l'API Bukkit (`CraftWorld.java:195-229`). Les chunks à moins de 128 blocs du spawn ne sont pas mis en file si `canRespawnHere()` et `DimensionManager.shouldLoadSpawn` (`ChunkProviderServer.java:120-141`) : vrai pour l'overworld (`keep-world-loaded: true`, `DimensionManager.java:84-88,447-451`, `run/cauldron.yml:18-24`), faux pour Nether et End (`canRespawnHere` faux, `WorldProviderHell.java:60`, `WorldProviderEnd.java:71`).
- Vidage : `unloadQueuedChunks` (508-587) à chaque tick de monde (`WorldServer.java:261`), MAIN, 100 chunks au plus par tick (524), sauté pendant `levelSaving` (510).
  - Il retire d'abord de la file tout chunk à ticket (513-519, balayage de tous les chunks forcés).
  - Il saute les chunks accédés ce tick quand des joueurs sont présents (535-539 ; `chunkGCGracePeriod` vaut 0 donc aucun retardement) ; le chunk sauté sort de la file et n'y revient qu'au prochain `unloadChunksIfNotNearSpawn`.
  - Pour les autres : `ChunkUnloadEvent` (543), `onChunkUnload` (550), `safeSaveChunk` sur MAIN (551), mise à jour des voisins, retrait des deux maps (567-568), cache dormant Forge (570), déchargement du monde s'il est vide et non gardé (571-574).
- Cache dormant : `ForgeChunkManager.putDormantChunk/fetchDormantChunk` (`ForgeChunkManager.java:898-925`), taille `dormantChunkCacheSize` = 0 par défaut (991-998, `run/config/forgeChunkLoading.cfg:44`) : aucun effet en l'état. GC de chunks Bukkit : `chunk-gc.enabled: false` (`run/bukkit.yml:33-36`, `CraftServer.java:244-246`).
- Chunk loaders Forge : tickets dans `ForgeChunkManager` (limites par défaut 200 tickets, 25 chunks par ticket, `forgeChunkLoading.cfg:33-40`) ; les chunks forcés sont rechargés et ajoutés à l'ensemble actif à chaque tick (`World.java:3473-3481`).

### Sauvegarde
- Autosave : `ticks-per.autosave` = 6000 ticks (`run/bukkit.yml:40`), `MinecraftServer.java:873-886` : `saveAllPlayerData` (un `.dat` par joueur, écriture synchrone via fichier temporaire, `SaveHandler.java:259-281`, plus `StatisticsFile`, `ServerConfigurationManager.java:349-360`) puis `saveAllWorlds(true)` (523-565), tout sur MAIN.
- Par monde : `WorldServer.saveAllChunks` (`WorldServer.java:1071-1106`) → `saveLevel` (1116-1122 : `level.dat`, `mapStorage.saveAllData`, `perWorldStorage.saveAllData`, écriture synchrone et complète de chaque `WorldSavedData` sale, `MapStorage.java:100-138`) → `ChunkProviderServer.saveChunks(true)` (466-498) → `flush()` (`MinecraftServer.java:542`).
- `saveChunks(true)` n'a pas de plafond : tout chunk `needsSaving` est sérialisé sur MAIN. Le plafond de 24 chunks (490-493) ne joue que pour `saveChunks(false)`, qu'aucun appelant du dépôt n'utilise (appels : `MinecraftServer.java:540`, `CommandSaveAll.java:48`, `CraftWorld.java:866`, `CraftServer.java:995`, tous avec `true`).
- `AnvilChunkLoader.saveChunk` (201-228), MAIN : `writeChunkToNBT` (304-427, entités 369, TileEntities 386, ticks 405), `ChunkDataEvent.Save` (221), `addChunkToPending` (230-252) → `ThreadedFileIOBase.queueIO`. Les tableaux `Blocks` (329), `Data`, `BlockLight`, `SkyLight` (336-341) sont mis dans le NBT par référence, sans copie (`NibbleArray.getValueArray` renvoie `data` quand il n'est pas trivial, `NibbleArray.java:89-93`) : le NBT n'est donc pas un snapshot des blocs.
- FIO : `ThreadedFileIOBase` (`E:net/minecraft/world/storage/ThreadedFileIOBase.java:23-63`) appelle `writeNextIO` (`AnvilChunkLoader.java:254-283`) sans pause (sommeil retiré par Spigot, 41-49) ; `writeChunkNBTTags` (285-290) : deflate (`DeflaterOutputStream`, `RegionFile.java:168`) puis écriture sous le moniteur du `RegionFile` (186). `chunksToRemove` est une `ArrayList` (`remove(0)` et balayages linéaires sous verrou, `AnvilChunkLoader.java:66-77,238-245,266`).
- `AnvilSaveHandler.flush` (`AnvilSaveHandler.java:51-63`) fait `waitForFinish` (attente active par pas de 10 ms, `ThreadedFileIOBase.java:74-84`) puis `RegionFileCache.clearRegionFileReferences()` (ferme toutes les régions) : MAIN attend la fin de toute l'écriture à chaque autosave et chaque monde.
- Données de structures : `MapGenStructureData` marqué sale à chaque structure (`MapGenStructure.java:289-293`), écrit par `saveLevel`. Désactivable : `save-structure-info` (`SpigotWorldConfig.java:187`, test à `MapGenStructure.java:243`) ; les mineshafts ne sont jamais persistées (même ligne).

## Pièges pour la suite
1. `RegionFileCache` : méthodes `static synchronized` partagées par MAIN, CIO et FIO ; au-delà de 256 régions, l'éviction (`deleteOldestReference`) appelle `File.lastModified()` sur toutes les entrées sous ce verrou et ferme la région la plus anciennement modifiée, pas la moins récemment utilisée (`RegionFileCache.java:43-45,57-84`). `RegionFile.close` n'est pas synchronisée (303-307) et les appelants gardent la référence après avoir quitté le verrou statique (`RegionFileCache.java:137-147`) : une lecture sur région fermée renvoie `null` (rattrapée par `safeLoadChunk`), mais une écriture FIO sur région fermée échoue en `IOException` simplement affichée (`RegionFile.java:266-268`), donc un chunk déchargé peut ne jamais atteindre le disque (scénario déduit de la lecture, à confirmer par test). Avec 400 joueurs dispersés, 256 régions de 32×32 chunks se dépassent facilement. À traiter avant tout agrandissement du pool.
2. `AnvilChunkLoader.chunkExists` est appelé sur MAIN pour chaque `loadChunk` et peut bloquer sur le moniteur d'un `RegionFile` en cours d'écriture ou de lecture (`RegionFile.java:109`) ; une file d'attente MAIN ne doit pas dépendre d'elle.
3. `finishActive` vide toute la file `finished` sans plafond (`AsynchronousExecutor.java:351-356`), et chaque étape 2 enchaîne `populateChunk` qui peut générer des voisins : une rafale de chunks (connexion ou téléportation : (2·DV+1)², soit 289 en distance 8, 625 au démarrage) tient en un seul tick. Le budget de finalisation doit couper entre deux étapes 2, pas à l'intérieur.
4. Ordre des générateurs de mods : `GameRegistry.generateWorld` itère le `HashSet` `worldGenerators` (`GameRegistry.java:123`), alors que Forge amont itère `sortedGeneratorList` (`eclipse/Clean/.../GameRegistry.java:109`) ; la liste triée est calculée mais inutilisée. L'ordre dépend du `hashCode` des générateurs, donc potentiellement non reproductible d'une exécution à l'autre : deux mondes générés avec la même graine peuvent différer, ce qui menace les tests de reproductibilité de la feuille de route et toute génération hors thread.
5. Les tableaux de blocs sont partagés par référence entre le NBT en attente et le chunk vivant (`AnvilChunkLoader.java:329-341`), pendant que FIO sérialise : un bloc modifié entre la mise en file et l'écriture peut produire une section incohérente. Un snapshot devra copier les sections, pas seulement le NBT.
6. `ChunkBlockHashMap` n'est pas thread-safe (cache `last1..last4`, `size++`) et sert de lecteur principal (`getChunkIfLoaded`) ; `loadedChunks` est une `ArrayList` nue ; `PlayerManager.playersWatchingChunk` et `players` sont des listes lues sur MAIN seulement. Toute écriture de chunk hors MAIN doit passer par une file vers MAIN.
7. `World.updateLightByType` : le décrément de `pendingLightUpdates` (`World.java:3917-3921`) est exécuté quand `!isModded && useAsyncLighting` alors que l'incrément (`World.java:4934,4943`) n'a lieu que si `isModded`; avec `use-async-lighting: true` les compteurs deviennent négatifs. Sans effet aujourd'hui, mais ne pas s'appuyer sur ces compteurs.
8. `crucible.chunkCacheSize` est trompeur : il ne règle pas la capacité du cache de régions (256 codé en dur). Un cache plus grand demande de modifier `RegionFileCache.java:43` et la politique d'éviction.
9. `ChunkProviderServer.loadChunk` avec callback exécute le callback tout de suite si le chunk n'est pas sur disque (206-210) : `PlayerInstance.loaded` passe à vrai après une génération synchrone, donc un budget de génération doit court-circuiter `PlayerInstance` aussi.
10. Cohérence de `unloadQueuedChunks` : un chunk « gardé pour activité récente » est retiré de la file sans y être remis (`popFirst` puis `continue`, 526-539). Un délai de déchargement doit ré-enfiler explicitement, sinon le chunk reste chargé jusqu'au prochain autosave (`WorldServer.java:1102`).
11. Le chargement d'un monde moddé peut accrocher `ChunkProviderServer.loadChunkOnProvideRequest` : `GameRegistry.generateWorld` le force à vrai le temps de la génération (`GameRegistry.java:121-122,140`), puis le restaure ; `CrucibleModContainer.reapplyConfigs` réécrit aussi ce champ pour tous les mondes (`S:io/github/crucible/CrucibleModContainer.java:287-290`). Une génération hors thread ne doit pas basculer ce champ global, et doit garder le chargement à la demande pour les mods qui lisent des chunks voisins pendant leur génération.
12. `ChunkPrefetcher` suppose que les chunks préchargés sont consommés par la boucle séquentielle (`NO_OP` comme callback, `ChunkPrefetcher.java:75`) ; il élargit le pool par un entier de joueurs (`threads * 50`, 107) car l'API n'expose pas la taille. Un pool de chunks dimensionné autrement doit remplacer ce détour, pas s'y ajouter.
13. Le thread `File IO Thread` est unique et partagé par tous les mondes et par d'autres `IThreadedFileIO` (`ThreadedFileIOBase.java:10`) ; `waitForFinish` est global, pas par monde.
14. Double chargement possible : une tâche CIO dont le chunk est chargé par un autre chemin que `loadChunk` (par exemple `CraftWorld.loadChunk(x,z,false)`, qui passe par `safeLoadChunk`) reste dans `tasks` ; `finishActive` rejouera alors l'étape 2 et réinsérera le chunk (`AsynchronousExecutor.java:169-201`, `ChunkIOProvider.java:36-77` sans test de présence). Déduit de la lecture, non reproduit. À garder en tête pour toute extension du préchargement au-delà du démarrage.
15. `recreateStructures` coûte 4 × 289 candidats par chunk chargé depuis le disque, sur MAIN (voir Chargement synchrone) : c'est un coût fixe de l'étape 2 que ni le pool ni le préchargement n'allègent.
16. `Chunk.func_150802_k()` renvoie toujours vrai (`Chunk.java:1253-1257`) : un chunk est envoyé avant sa population ou son éclairage, et les corrections arrivent ensuite par paquets de blocs. Une décoration différée avec budget produira donc des chunks visibles non décorés, sauf si ce test est rétabli pour les chunks en attente.
17. `PlayerInstance.playersWatchingChunk` (`ArrayList`) et la copie de `EntityPlayerMP.loadedChunks` (`LinkedList`) sont parcourues par `contains` : coût quadratique du déplacement avec la distance de vue (`PlayerManager.java:185-235,413`, `EntityPlayerMP.java:133`).
